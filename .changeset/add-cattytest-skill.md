Add the `cattytest` skill (engineering bucket, user-invoked). A grilling session for the developer who has code and no idea how to test it. It asks one scope question (current feature or ticket, or the whole project), reads the feedback loops, the ticket, `CONTEXT.md`, the existing tests and the code's outside-world boundaries, then interviews in rounds along nine branches: stakes, claims, seams, oracle and level, doubles, data, wrong paths, existing tests, budget. Every question carries a recommended answer drawn from the repo; the user corrects sentences, never enumerates code. Output is a `test-plan.md` beside the spec (or a `Test plan:` issue on a real tracker): numbered business-rule claims in `CONTEXT.md` words, each with a confirmed seam, a level, an oracle and a doubles decision, a keep / rewrite / delete sort of the existing tests, and the first red tests in order, sized to be finished. Claims the user cannot confirm stay in the plan flagged, never assumed. Plans and does not write tests; on go it drives `tdd` through the first red tests, and `test-audit` later reads the written tests back as the same list of claims. `vibe` routes "I don't know how to test this" to it.
